# codex-spec

A coding agent can report success while the requested behavior is missing, tests were never run, or an existing feature regressed. Even a passing test result can become outdated after the next edit. Developers need an explicit definition of done and evidence that the current code meets it.

**Codex implements the change. codex-spec defines and checks what “done” means.**

codex-spec is a Codex-native skill with readable Markdown specs and a dependency-free verification runner. Keep the requirements and acceptance checks together in `spec.md`, let Codex implement the change, and collect results tied to the spec and code that were tested. If either changes, the verifier detects that the evidence is stale.

Use it for features, bug fixes, refactors, and performance work where “the agent finished” is not enough to accept a change.

## What it does

1. **Spec:** capture intent, constraints, and observable acceptance criteria.
2. **Implement:** let Codex explore, plan, edit, and iterate using its native tools.
3. **Verify:** run explicit checks and associate their results with criteria and a fingerprint of the code and contract.

Only passing acceptance checks against an unchanged workspace produce `verified`. That label describes automated acceptance coverage, not proof of correctness or permission to merge.

## Quickstart

Requires Node.js 22+ and Git. Verification supports macOS and Linux. The toolkit needs no dependency installation or API key. Using the skill for implementation also requires a configured Codex environment.

Clone the repository and try the runnable demo:

```bash
git clone https://github.com/shenli/codex-spec.git
cd codex-spec
node scripts/demo.mjs
```

The demo creates a temporary Git repository and demonstrates `failed → verified → stale` using real tests. It prints the repository and evidence paths for inspection. See [the demo guide](DEMO.md) for details.

To start a feature in this checkout:

```bash
node src/cli.js spec rate-limiter "Limit each API client to 100 requests per minute"
```

This creates only `.codex-spec/features/rate-limiter/spec.md`. The scaffold contains an incomplete criterion, so it cannot pass verification until you add a concrete check or review procedure. Existing feature directories are never overwritten.

The final feature directory contains:

```text
.codex-spec/features/rate-limiter/
  spec.md            You edit: intent, constraints, acceptance criteria, and checks
  evidence.json      Generated by verify; do not edit
```

In Codex, invoke the bundled skill:

```text
$spec-driven-development Refine the rate-limiter contract, then implement
it within the agreed scope and run its acceptance checks.
```

Or use native non-interactive Codex:

```bash
codex exec --sandbox workspace-write \
  'Use $spec-driven-development to implement .codex-spec/features/rate-limiter. Follow the contract and run verification.'
```

Codex handles its own authentication, model configuration, permissions, and context. codex-spec does not launch another agent or manage sessions.

Edit `spec.md` to describe each acceptance criterion and its verification command. Then run:

```bash
node src/cli.js verify rate-limiter
node src/cli.js status rate-limiter
```

Both commands print JSON. Verification executes the commands in the contract, so inspect that file as you would a build script.

## Write the spec

Edit `.codex-spec/features/rate-limiter/spec.md` directly or ask the skill to help. For example:

```markdown
# Rate limiter

Limit each API client to 100 requests per minute.

## Acceptance criteria

### Request limit
The first 100 requests succeed.
Request 101 within the same minute returns HTTP 429.

Verify: `node --test test/rate-limit.test.js`

### Compatibility
Existing API behavior remains compatible.

Verify: `npm test`
```

This is the whole contract. There are no IDs, argument arrays, readiness flags, or second files to maintain. The verifier reads Markdown directly and generates its internal mappings and evidence.

The example assumes your project has the named test file and an `npm test` script. Replace them with checks that actually assert the described behavior; the scaffold does not generate tests.

Use one `Verify:` line per command, beneath a uniquely named `###` criterion in `## Acceptance criteria`. Commands run from the repository root with a two-minute timeout by default. Add `Directory: web` or `Timeout: 30s` beneath a criterion when needed. Identical commands with the same directory and timeout run once and share their evidence.

Commands support ordinary quoting and run without an implicit shell. Put pipes, command chaining, or environment setup in a test/package script. Malformed directives are errors, and any criterion missing both `Verify:` and `Review:` blocks all command execution.

For human acceptance, use `Review:` followed by a specific procedure, such as `Review: Inspect the API diff and record the decision in the PR.` Manual review keeps the overall automated gate blocked, even if its other checks pass; the tool cannot attest human approval.

See the [contract and evidence reference](.agents/skills/spec-driven-development/references/contracts.md) for the full format and limits.

## Use the skill in another repository

From the codex-spec checkout, copy the **whole** skill directory, including its scripts and references, into your target Git repository:

```bash
mkdir -p /path/to/project/.agents/skills
cp -R .agents/skills/spec-driven-development /path/to/project/.agents/skills/
cd /path/to/project
node .agents/skills/spec-driven-development/scripts/codex-spec.mjs \
  spec rate-limiter "Limit each API client to 100 requests per minute"
```

In the target repository, invoke `$spec-driven-development` in Codex. Use the copied helper for verification and status:

```bash
node .agents/skills/spec-driven-development/scripts/codex-spec.mjs verify rate-limiter
node .agents/skills/spec-driven-development/scripts/codex-spec.mjs status rate-limiter
```

No global install is required. The skill is self-contained. If you prefer the short `codex-spec` command, run `npm link` from the codex-spec checkout. The npm entry point uses the same implementation as the skill.

## Commands

Run from a Git working tree. Feature names are lowercase hyphenated slugs, such as `rate-limiter`; quote the intent as one argument.

| Command | Action |
| --- | --- |
| `spec <feature> "<intent>"` | Create a new Markdown scaffold without overwriting existing work |
| `verify <feature>` | Execute declared checks and write evidence |
| `status <feature>` | Check current evidence and freshness without running commands |
| `--help` / `--version` | Show usage or version |

Use `node src/cli.js` from this checkout, the copied helper in another project, or `codex-spec` after linking. Planning and implementation happen in Codex; there is no separate implementation command.

## Verification semantics

| Result | Meaning | Exit code |
| --- | --- | --- |
| `verified` | Every declared automated criterion passed; inputs stayed unchanged | 0 |
| `failed` | A check failed, timed out, was interrupted, or could not start | 1 |
| `blocked` | Missing check/review, manual review outstanding, or lock detected by `status` | 1 |
| `stale` | Code, HEAD, or contract no longer matches the tested inputs | 1 |
| `unverified` | No evidence exists | 1 |
| `invalid` | Invalid contract/evidence or verification infrastructure error | 2 |

`spec`, help, and version exit 0 on success. Usage errors exit 2. A second `verify` attempt while a run is locked exits 2; `status` reports that lock as blocked (exit 1).

Evidence includes criterion mappings, exact arguments, timestamps, duration, exit codes, signals, bounded stdout/stderr, and before/after workspace hashes. Status recomputes freshness and validates result coverage instead of trusting a saved status label. Running verification replaces the previous receipt atomically; archive receipts in CI for run history.

The fingerprint covers Git HEAD, tracked files (including modifications and deletions), nonignored untracked files, executable bits, symlink targets, and the current contract even if ignored. Generated evidence and the verification lock are excluded. Ignored dependencies/build output, external symlink contents, environment variables, databases, and remote services are outside the fingerprint. This is local, unsigned evidence from trusted checks, not an isolated sandbox or tamper-proof attestation. Submodules fail closed rather than silently receiving partial coverage.

Tests should not modify source files. If they do, evidence becomes stale; fix the check or rerun once the workspace is stable. A passing test only supports the behavior it actually asserts—review the criterion-to-test mapping.

## Development and CI

```bash
npm test
npm run check
node src/cli.js verify verification-gate
npm pack --dry-run
```

The checked-in `verification-gate` contract exercises the toolkit itself. CI is configured to run the tests and contract gate on Linux/macOS with Node.js 22/24, then archive evidence. It requires no Codex credentials.

Keep `AGENTS.md` concise and stable. Read architecture and product documentation when relevant to a task; there is no generated context-refresh cycle.
